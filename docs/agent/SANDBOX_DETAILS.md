## 扩展加载（issue #7）

- **批量验收台架**：隔离根 `E:\Github\Suwayomi-builds\ext-lab`（沙盒 **4599**）。根下 `db/suwayomi.db` 是种子库（仓库索引 + 扩展元数据，`ext_survey.py` 靠它拿 apk_url）、`extensions/apk/` 放 APK、`extensions/bin/` 放转好的 jar（根就是 appdata 根，见下）。`ext_probe.py` 管起停（单包快验用探针根 `ext-probe`/4601，全量用 `--root …ext-lab --port 4599`；`--no-system-proxy` 起直连那条腿），`ext_survey.py` 出报告（`--sandbox http://127.0.0.1:4599 --langs zh,zh-Hans,zh-Hant,all --tag fixN`；**`--langs` 必须对齐台架里真实有的 APK 集合**，`--skip-download` 只统计缺哪些、不收敛 `rows`，传错会把种子库 1395 行全算进来），`ext_usability.py` 量真实可用性（每包 1 源，真打请求），`ext_consistency.py` 查扩展↔源归属自洽（可加 `--concurrent N` 压并发 `/reload`），`ext_failures.py`（按最深 cause 归类）/ `ext_trace.py`（打印单包全栈）查根因。**沙盒能脱离 Rust 服务端单独起**（只读 `SUWAYOMI_SANDBOX_PORT` / `SUWAYOMI_APPDATA_DIR` 两个环境变量；扩展目录 `extensions/apk`、转换产物 `extensions/bin`、设置目录 `settings` 都由 appdata 根派生，子路径与 Rust 侧 `AppPaths` 必须一致），改沙盒代码后没必要起整个实例。
- **常驻沙盒必须用后台任务起**：普通 Bash 调用里的子进程会随父 shell 的 job object 一起被杀（症状是「刚 `/health` 通，几十秒后连接被拒」）。
- **实测结论**：192 个扩展（langs=zh,zh-Hans,zh-Hant,all）**43.2% → 100%（192/192、1183 个源、零「装上但无源」）**；收尾又修掉一处归属错位（下一段），修前那条假跌到 86/192 的报告本身是台架数据不自洽，不是扩展坏了。收尾补的两处缺口：① 共享源码树从来没有 `eu.kanade.tachiyomi.AppInfo`（extension-lib ≥1.3 宿主面，扩展拿它拼 User-Agent）→ 新增 `ext-runtime/src/shared/kotlin/eu/kanade/tachiyomi/AppInfo.kt`，版本由 server spawn JVM 时经 `SUWAYOMI_VERSION_NAME` / `SUWAYOMI_VERSION_CODE` 注入（`sandbox/AndroidEnv.kt::installHostVersion`），Android 由 `ExtensionHost.start` 读本应用包信息；② vendored `AndroidCompat-1.0.jar` 的 `Build`/`SystemProperties` 静态依赖 `xyz.nulldev.ts.config.ConfigManager`（在 `Suwayomi-Server/AndroidCompat/Config` 模块，未打进该 jar）→ 引 `libs/Config-1.0.jar` + typesafe-config + config4k + appdirs（jar 35.5MB → 39.4MB），并自备 `resources/server-reference.conf`（只补 `server.debugLogsEnabled`）。
- **剩下 `cubari` 属结构性不可用（加载成功、浏览不可能）**：它的 Home/Popular/Latest/Search 都走 `RemoteStorageUtils` 拦截器 —— `chain.proceed()` 之后把响应体换成**隐藏 WebView** 里取到的 payload，而 `q.onPageFinished` 注入的 JS 调的是 cubari.moe **站点自己的前端模块** `globalHistoryHandler`（读用户浏览器的 pinned/history 状态）。要真能用等于要真浏览器；补 `android.view.ViewTreeObserver` 也没用（`WebView.loadUrl` 本身就是空 stub，payload 恒空）。参考实现 Suwayomi 同样跑不了它。`mangaDetails`/`chapterList`/`pageList` 是纯 HTTP，但加系列的入口（按 URL 搜索）也被拦。
- **「加载率暴跌、失败清单却一条都没有」= 扩展↔源归属错了**。桌面 `ExtensionRegistry` 曾经把 `extensionId` 做成**读时**从活的 map 算（`extensions.size + 1`），而 `scan()`/`reload()` **没有互斥**：宿主是多线程 executor，并发 `/reload` 交错时后一轮 `clear()` 掉前一轮刚写下的东西 → `extensions.size` 不再增长（覆盖写不涨 map）→ **一批包拿到同一个 id**，`sources[it.id] = it` 又互相覆盖。序列化再用 `sources.values.filter { it.extensionId == e.extensionId }` 反查，重号的扩展就集体变成「零源」。日志指纹：某条 `/reload` 打了 **422** 条 `loaded N source(s)` 只报 **144** 个扩展，下一条只打 **154** 条却报 **192**（前一轮残留）；另有一条 `extensions=144 sources=693 (1s)` —— 1 秒扫不完 192 个包。修法：`scan()`/`reload()` 加 `@Synchronized`（Android 侧 `PackageManagerRegistry` 早就这么做、注释里就写着这个风险）；id 改由扫描自持的计数器分配、只在新包注册成功时推进、重扫到的老包**沿用原号**（否则旧号名下的源变孤儿）；归属在加载时记进 `sourcesByExtension`，不再反查。`/extensions` 现在也输出 `extensionId`（两端同形，位置同 `/inspect`；Rust `SandboxExtension` 无 `deny_unknown_fields`，多字段无副作用，它本来就按 `pkg_name` 认扩展）。
- **判数要过自洽性**：`.workbuddy/verify/ext_consistency.py` 核三条不变式（extensionId 唯一 / 每个源挂在存在的扩展上 / 两侧源总数相等），`ext_survey.py` 也内置同一套并写进报告的 `consistency_problems`。改过 `scan()`/`reload()` 的锁之后必须跑 `--concurrent 3 --rounds 2`。
- **加载率 ≠ 可用率，且只跑一条网络腿会低估一半**：`ext_usability.py` 每包挑一个源打真实请求。本机（Clash）代理腿 **132/192=68.8%**、直连腿 **85/192=44.3%**、**并集 145/192=75.5%**（60 个只有代理通、13 个只有直连通）。直连那条腿要换沙盒启动参数（`ext_probe.py --no-system-proxy`，系统代理是 JVM 进程级开关），量完换回默认。两腿皆失败的 47 个全是站点侧（403×16 / TLS×5 / 502·521·522·404 / 站点改版 / 需配置 / 需账号）+ `cubari`。
- **真实实例上冒烟要手动搬沙盒 jar**：`deploy_latest.py` 只镜像 `suwayomi-server.exe` 与 `webui/`，**不管 `bin/ext-runtime.jar`** —— 自己停实例、cp（先留 `.bak-<时间戳>`）、再拉起托盘。验收看 8091 的 `/health` + `ext_consistency.py`，再对一遍 server 侧库存 —— 实例库的表**不带 schema 前缀**（`SELECT e.pkg_name, COUNT(s.id) FROM extension e LEFT JOIN source s ON s.extension=e.id WHERE e.is_installed GROUP BY 1`），写 `suwayomi.extension` 会报 `no such table`。
- **AndroidCompat 的 `Looper.loopOnce` 只 `catch(Exception)`**，`Error` 会直接穿出 `loop()` 打死主 looper 线程 → 之后所有 `post` 静默失效、在 `CountDownLatch.await` 上等的扩展只能等到超时。`sandbox/AndroidEnv.kt::startMainLooper` 里兜 `Throwable` 并重新进入 `loop()`（队列被 quit 时 `loop()` 正常返回，不再重启）。
- **Android stub 全部由构建产出，仓库里不再放 jar**：AndroidCompat 与其 Config 模块是源码子项目（`ext-runtime/android-compat/`、`android-compat/config/`，三方依赖一律 `compileOnly`，产物只含自己的类）；AOSP 公开 API 空壳由 `ext-runtime/android-stub/` 在构建期按 `android-stub.properties` 的 pin 下载并剥离后生成，版本号 = `<AOSP API level>.<平台包修订>.<剥离修订>`。**别再改回参考实现用的 `com.github.Suwayomi:android-jar:1.0.0`** —— 那个坐标**可变**：同一个 `1.0.0` 下内容被原地覆盖过 7 次（2021-09-28 → 2025-12-17），分支只有 maven 目录树、没有构建脚本，Gradle 按坐标缓存所以拉到哪一版全看缓存。源改用 dl.google.com 的 `platform-<api>_r<NN>.zip`（googlesource 在部分网络 TCP 不通，绕开沙盒也一样；`-PaospPackageUrl=<mirror>` 可换镜像，sha256 仍校验）。剥离集合**按源码路径推导**（同 `getAndroid.sh`）——不能读编译产物，否则 `:android-stub:jar` → `:android-compat:jar` → `:android-stub:jar` 成环；推导漏项由根项目 `verifyStubDedup` 兜底（两 jar 同名类直接 fail）。基线溯源写在 `META-INF/android-stub.properties`，随 fat jar 走：`unzip -p bin/jvm-sandbox.jar META-INF/android-stub.properties`。
- 三条容易踩的硬事实：
  1. **`Dex2jar` 门面无法插桩**（optimize 链写在匿名子类里）→ 用 `ExDex2Asm` 子类覆写 `optimize` 自己驱动转换（见 `DexTranslator`）。
  2. **必须把 APK 的 `assets/**` 搬进 jar，且保留 `assets/` 前缀**——keiyoushi 1.6 的 i18n 查找名就是 `assets/i18n/messages_xx.properties`。dex2jar 只产出 class，不搬资源。
  3. **改动转换链产出内容后必须 +1 `CONVERTER_VERSION`**，否则 `bin/extensions` 里按文件名缓存的旧 jar（`<appdata>/extensions/bin`） 会一直被用。
- **共享源码的 `HttpSource` 是 Mihon 契约**：`searchMangaRequest` 默认 `throw UnsupportedOperationException()`，所以 coomer 这类不支持搜索的源在 `/source/{id}/manga?query=` 上 500 是**正常行为**；komga 的 `baseUrl` 来自用户配置的服务器地址，沙盒里为空 → `Expected URL scheme 'http' or 'https'`，同样不是缺陷。
- 单包深挖用 javap：`"C:/Program Files/Eclipse Adoptium/jdk-25.0.4.7-hotspot/bin/javap" -p -c -cp <转好的jar> <类>`，配合 R8 混淆后的名字（`o`/`p`/`n`/`Generated`）能直接读出扩展到底调了什么。
- **`SourceDriver.callFetchOrSuspend` 必须按「方法由谁声明」选路，不能只「legacy `fetch*` 先试、抛异常再回退」**：框架 `HttpSource.fetchPageList` 是模板实现（`pageListRequest` 默认 `GET(baseUrl + chapter.url)`），它**不抛异常**，只到 `pageListParse` 才抛 → 扩展自己实现的 suspend `getPageList` **永远不会被调用**。`chapter.url` 是绝对地址的源（哔咔：API `picaapi.picacomic.com` 与阅读站 `manhuabika.com` 不同域）被拼成 `https://manhuabika.comhttps://picaapi…`，主机名畸形 → TLS 握手被对端掐断，表现为 `/pages` 恒 500 `SSLHandshakeException`。`isExtensionOwnMethod(obj, name, paramCount)` 沿父类链找**最先声明**该方法的类，落在 `eu.kanade.tachiyomi.source.**` 之外（R8 后扩展类是 `keiyoushi.source.Generated` / `a0` 之类）即算扩展自己的实现；老 lib（只 implement `fetch*`）判定为框架 → 仍走 legacy，行为不变。`callMangasPageMethod`（popular/latest/search）**不受影响**：框架那几个 `fetch*` 直接 `throw UnsupportedOperationException`，回退本来就正常。详情/章节也没露，因为 `SourceDriver` 对这两条先走 `getMangaUpdate`。
- **判「扩展的请求失败是网络还是代码」的两个零代码仪器**：① `JAVA_TOOL_OPTIONS=-Djavax.net.debug=ssl:handshake`（`spawn_java` 继承环境变量，不用改代码）→ `sandbox.log` 打出每次握手的 **SNI**，能直接看到请求的真实主机名；② `.workbuddy/verify/connlog_proxy.py` + `SUWAYOMI_SANDBOX_PROXY=127.0.0.1:18899`（上游转发到本机 Clash 7890，保证 picaapi 这类必须走代理的主机仍可用）→ 按顺序打出**每个 CONNECT 目标**。注意 `NetworkHelper` 的 `[okhttp]` 日志是 `addNetworkInterceptor`，**连接建立失败时拦截器根本没跑到**，所以「日志里没有这条请求」不等于「没发请求」。
